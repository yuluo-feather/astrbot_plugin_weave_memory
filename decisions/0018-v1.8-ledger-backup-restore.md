# ADR-0018：V1.8 ledger-first 删除与备份恢复

状态：Accepted（实现随 V1.8 落盘）
日期：2026-11-23

## 背景

V1.8 要在 V2 平台迁移前提供可回滚底座：删除/清空/consent/群销毁必须先落权威意图，再改主库；恢复旧备份时不能复活已删除、清空或撤销授权的内容。主库删除仍保留 V1.0 的墓碑、FTS dirty 与物理擦除语义。

## 决策

### 1. 独立账本

- 账本文件为 `<data_dir>/memory_ledger.sqlite3`，与主库分离，不进入备份包。
- 只追加事件：`delete_memory`、`clear_scope`、`consent_change`、`remove_attachment`、`destroy_scope`；每种事件由同一 `event_id` 的 `intent` 与 `committed` 两条记录组成。
- `seq` 全局单调；`ledger_id` 首次创建生成，轮转不变；每个文件记录 `base_seq` / `end_seq`，`earliest_retained_seq` 随轮转推进。
- 轮转把活动文件移入 `memory_ledger_segments/`，不裁剪事件；读取恢复时会遍历全部分段。
- `synchronous=FULL` + WAL：intent 提交先于主库变更；主库失败时 intent 保持 pending，启动和备份前重放。

### 2. 主库谱系与序号（schema v9）

- `memories` 增加 `db_lineage_id` 与 `creation_seq`，唯一键 `(db_lineage_id, creation_seq)`；两者 NOT NULL。
- `memory_meta.db_lineage_id` 是当前新行使用的谱系；`memory_lineage_meta` 持久化每个谱系的分配高水位，只增不减。
- 所有创建路径在 `WriteCoordinator` 写租约内由 `SQLiteMemoryStore` 原子分配 `creation_seq`；V1.7 导入忽略源序号。
- `clear_scope` payload 记录每个受影响谱系的 `clear_creation_seq`/`high_watermark`，删除谓词为 `scope_id + db_lineage_id + creation_seq <= boundary`。
- 迁移 `009_lineage_ledger.sql` 重建 `memories` 回填 `(created_at, id)` 顺序序号，并写入 `memory_lineage_meta`。
- 回滚为特征级：保留列与分配器，移除 v9 schema 标记并配置 `ledger_first_enabled=false`；备份/恢复同时禁用。

### 3. 备份

- 目录 `<data_dir>/backups/v1.8/<utc>-<db_lineage_id>/`，含 `main.sqlite3`、`sidecar.json`、`config.json`（脱敏）、`README.txt`。
- `sidecar.json` 记录格式版本、`schema_version`、`db_lineage_id`、`ledger_id`、`ledger_seq_at_backup`、`creation_seq_at_backup`、`lineage_high_watermarks`、`sha256`、`size`、分表行数。
- 备份在写租约内完成：先 drain pending，再主库 SQLite 在线快照，再采集水位；失败即中止。
- 保留策略默认最近 5 份且 30 天，不删除最新一份。

### 4. 恢复

- 模式：`merge`（默认）、`revert`（显式覆盖同 ID）、`disaster-rebuild`（空目标 + 新当前谱系）。
- 先校验备份哈希、schema、`ledger_id`、分段连续性与 seq 覆盖；`merge`/`revert` 还要求当前 `db_lineage_id` 与备份一致。
- 恢复前创建快照并写 `restore_journal.json`（原子 rename + fsync）；启动时若 journal 未完成则先重做，损坏/缺失即 fail closed。
- 先合并/覆盖备份表，再按 `seq > ledger_seq_at_backup` 重放排除；被排除的 memory 在合并阶段就跳过，避免触发唯一索引。
- 重放覆盖 `delete_memory`、`clear_scope`、`remove_attachment`、`destroy_scope`、`consent_change`；consent 取最新事件状态。
- 恢复后重建 FTS，推进 `memory_lineage_meta` 高水位并清理导入任务中的失效 memory ID。

### 5. 入口与配置

- 命令：`/织忆 备份 [列表]`、`/织忆 恢复 <备份ID> [merge|revert|disaster-rebuild] 确认`（仅私聊；未加“确认”为 dry-run）。
- 管理 API：`POST /v1/maintenance/backup`、`POST /v1/maintenance/restore`、`POST /v1/maintenance/reindex`；要求非空 `api_admin_usernames` 白名单与 `confirm=true`。
- 配置：`ledger_first_enabled`、`ledger_rotate_events`、`backup_keep_last`、`backup_retention_days`。

## 限制

- 仅支持同一实例主库的备份；跨实例/跨平台共享不在 V1.8。
- 账本与主库同盘同时丢失时，无法保证旧备份排除删除；运维需单独轮转/备份账本。
- V1.8 之前的旧备份没有 `destroy_scope`/`remove_attachment` 事件，恢复时显式不保证排除。
- 删除/清空的物理擦除仍是 SQLite 级（`secure_delete` + checkpoint/VACUUM），不是 SSD 取证级保证。

## 后果

- 删除/清空/consent/群销毁的权威意图可重放；旧备份不能复活已撤销的数据。
- 备份/恢复具备显式模式、水位校验与崩溃恢复路径，为 V2.3 迁移提供回滚底座。
- schema v9 的列与分配器在回滚后保留，V1.7 语义仍可运行。
