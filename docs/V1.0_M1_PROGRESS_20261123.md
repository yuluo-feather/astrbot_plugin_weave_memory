## 3. M1 第一批实现

### 3.1 显式保存幂等

- 新增 `MemoryStore.find_active_duplicate`，按 scope、subject、memory_type、normalized_content 查找 ACTIVE 记忆。
- 新增 `WriteCoordinator.create_or_get_duplicate`，在同一进程写锁内完成查重与创建。
- 重复保存返回原 memory ID 与 revision，不新增 memory/revision/source。
- SQLite partial unique index 保留为最终并发/一致性约束。

### 3.2 显式更新

- 新增 `MemoryApplicationService.update_explicit`，调用者必须指定 memory ID 与 expected revision。
- 仅允许 ACTIVE 记忆更新；更新必须经过 Consent 和 Scope 校验。
- 成功更新递增 revision，追加 Source；正文、Revision、Source 由 SQLite 同一事务提交。
- 旧 revision 返回 Conflict；不会静默覆盖。
- 更新后 FTS 通过既有 dirty marker / sync 流程更新。

### 3.3 检索排序与访问时间

- FTS 先过滤 scope、subject、consent 对应的 scope enabled、ACTIVE 状态与语义有效期，再执行 BM25 排序和 LIMIT。
- BM25 相关性为主；相关性相同按最近访问时间（无访问记录回退创建时间）、EXPLICIT 来源优先、MemoryType/ID 稳定打破平局。MemoryType 只作末级 tie-break，未声称权重已校准。
- `MemoryStore.record_access` + `WriteCoordinator.record_access` 统一记录访问元数据，不增加 Revision、不触发 FTS dirty。
- Composer 仅为实际选入上下文的记忆记录访问；手动查询记录实际返回的记忆。
- Composer 与 AstrBot Injector 改为 async，以等待访问元数据通过 WriteCoordinator 写入。

### 3.4 SQLite v3 → v4 与关系表占位

- 增加 migration `004_memory_relations.sql`，schema version 从 3 升到 4。
- 关系表仅保留最小有向边结构，不提供关系 API，不参与检索。字段细节以 ADR-0007 标注为实现选择。
- 单条删除与 Scope 清空在权威事务内清理所有关联入边/出边，避免悬空外键。
- 新增 v3→v4 升级测试、单条删除关系清理测试、跨 Scope 清空关系清理测试。

### 3.5 V1.0 → V0.5 Schema 回滚

- 增加 `SQLiteDatabase.rollback_to_v05()`，只在 `memory_relations` 为空时回退 v4→v3。
- 关系表非空时拒绝回滚，保留数据与 schema 版本；没有静默丢弃。
- 新增空表回滚/重新迁移与非空拒绝回滚测试。

### 3.6 Scope 关闭与 Consent 联动

- LifecycleService 现在依赖 ScopeStore + ConsentService。
- 关闭先提交 Scope disabled，再追加 `personal_memory=REVOKED` 事件。
- 注入故障测试验证 Consent 追加失败时 Scope 仍不可读；相同 operation ID 重试可补齐撤销事件，不重复关闭操作。

### 3.7 M3 并发/故障专项（首批）

- 同一记忆两个并发更新使用相同 expected revision：仅一个成功，另一个 Conflict。
- 模拟 FTS 返回候选后、权威读取前发生删除：Recall 丢弃 NotFound 候选。
- 模拟 FTS 表在更新前丢失：权威新版本提交并回执 PENDING_REBUILD；启动恢复后检索到新正文、旧正文不可见。
- Coordinator.close 等待当前写锁，关闭后排队写入返回 ServiceClosed。
- 模拟 Recall 命中后、访问记录前发生 Consent revoke/Scope disable：Composer 不返回上下文；撤销时不写 last_accessed_at。
- 模拟显式保存/更新入口检查后、写锁获得前撤销 Consent：Coordinator guard 拒绝写入，权威数据不变。
- Consent 撤销追加故障时 Scope 仍关闭；同 operation ID 重试补齐撤销事件。

### 3.8 AstrBot 命令入口

- 新增 `/记忆 更新 <记忆ID> <当前revision> <新内容>`。
- 更新必须显式指定 ID 与 revision；旧 revision 返回 Conflict。
- `/记忆 查询` 改为异步，以便记录实际查询访问时间。

## 4. 验证

命令：`python -m pytest -q`
归档基线复跑：`94 passed`（Python 3.13.5）。在本轮新增迁移失败原子性测试后：`96 passed`（Python 3.13.5）。

新增测试：
- 同一规范化内容重复保存返回同一 ID；不新增 revision/source。
- 8 个并发显式保存请求只产生一条记忆。
- 显式更新 revision 递增、source 追加、FTS 内容同步。
- 旧 revision 更新返回 Conflict，权威记录保持不变。
- InMemory Store 的查重严格按 scope/subject/type/content 隔离。
- 检索按最近访问时间打破 BM25 同分候选；访问只记录最终注入或手动查询返回项。
- AstrBot 命令层显式更新成功、revision 递增，旧 revision 冲突可见。
- SQLite v3→v4 升级、关系入/出边删除级联均通过集成测试。
- Scope 关闭后 Consent 撤销；撤销写入失败后重试恢复一致，Scope 始终 fail-closed；AstrBot 命令准确提示“已关闭、撤销待重试”。
- 并发更新、删除/召回边界、FTS 更新失败后启动恢复、Coordinator 关闭等待均有专项测试。
