# V1.0 M3 崩溃恢复专项报告（2026-11-23）

状态：自动化进程终止专项通过；不等同于断电/存储介质故障验证。
基线：最新完整工作区 `weave_memory_v1.0_m3_updated_workspace.zip`。

## 1. 测试环境与执行

- Python：当前执行环境 Python 3.13。
- SQLite：项目 `SQLiteDatabase` 配置 WAL、`busy_timeout=5000`、文件数据库 `synchronous=FULL`。
- 命令：`python -m pytest -q`。
- 结果：**100 passed**（当时基线；2026-11-23 P3 补测后 132，V1.1 实现后 143）。

本专项新增 `tests/integration/test_crash_recovery.py`，通过独立子进程打开同一 SQLite 文件，在明确的事务边界暂停后由父进程强制终止子进程，再重新打开数据库验证恢复状态。

## 2. 覆盖场景

| 场景 | 终止点 | 重启后预期 | 结果 |
|---|---|---|---|
| 未提交权威事务 | `BEGIN IMMEDIATE` 后插入数据、尚未 COMMIT | 未提交行回滚，既有行保留，schema 仍可读 | 通过 |
| 已提交事务后进程退出 | COMMIT 完成后立即 `os._exit(0)` | 已提交数据保留 | 通过 |
| v3→v4 迁移中断 | DDL 与 v4 marker 已执行但事务未提交 | DDL 和 marker 一起回滚；重启后可重新迁移至 v4 | 通过 |
| FTS 脏状态持久化 | 权威数据保留，dirty marker 与索引差异提交后进程立即退出 | 启动恢复从权威表重建 FTS，索引恢复健康 | 通过 |

## 3. 结果解释

- SQLite WAL 在进程被强制终止后能够回滚未提交事务；已提交事务在当前 `synchronous=FULL` 配置下可在进程退出后恢复。
- 迁移 DDL 与 schema version marker 位于同一 SQLite 事务中，进程终止不会留下“部分 DDL + 错误版本号”的半迁移状态。
- FTS 是派生索引。权威数据与 dirty marker 已提交、索引尚未修复时，启动恢复可重建索引，不依赖旧 FTS 内容。

## 4. 明确未覆盖

本报告不能证明以下场景：

- 物理断电、虚拟机硬复位、磁盘控制器/设备写缓存丢失。
- 文件系统损坏、磁盘坏块、数据库文件与 WAL 文件被外部程序同时破坏或删除。
- 多进程同时写入；V1.0 仍是单进程、单实例设计。
- 在真实 AstrBot 进程中执行外部强杀后，再由真实宿主自动加载插件的完整端到端演练。

因此，本轮结论应表述为“SQLite 进程异常终止恢复专项通过”，不得写成“断电级恢复已验证”。
